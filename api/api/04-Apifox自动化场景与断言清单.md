## 二、场景一：博客主流程-接口自动化

执行顺序即下表顺序，后一步依赖前一步产生的登录态与 `bid`。

| 步骤 | 接口 | 方法与路径 | 关键参数 | 断言 | 变量处理 | 实际结果 |
|---|---|---|---|---|---|---|
| 1 | 登录 | POST `/login` | Body(x-www-form-urlencoded)：`username=admin`、`password=123456` | HTTP Code 等于 **200** | 自动保存并复用 `JSESSIONID` | 通过 |
| 2 | 博客列表（分页） | GET `/blog/{page}/{limit}` | Path：`page=1`、`limit=10` | HTTP Code 等于 **200** | — | 通过 |
| 3 | 发表博客 | POST `/blog/write` | Body：`title=接口测试自动发帖`、`content=...`、`authorId=1`、`authorName=admin`、`authorAvatar=/img/avatar.png`、`categoryId=1` | HTTP Code 等于 **200** | 后置操作：从响应文本中正则提取 `bid` 并写入临时变量 | 通过 |
| 4 | 博客详情 | GET `/blog/read/{bid}` | Path：`bid={{bid}}` | HTTP Code 等于 **200** | 引用临时变量 `{{bid}}` | 通过 |
| 5 | 发表博客评论 | POST `/blog/comment/{bid}` | Path：`bid={{bid}}`；Body：`topicId={{bid}}`、`userId=1`、`userName=admin`、`userAvatar=/img/avatar.png`、`content=接口测试评论` | HTTP Code 等于 **200** | 引用临时变量 `{{bid}}` | 通过 |
| 6 | 删除博客 | GET `/blog/delete/{uid}/{bid}` | Path：`uid=1`、`bid={{bid}}` | HTTP Code 等于 **200** | 引用临时变量 `{{bid}}` | 通过 |

### 步骤 3 的变量提取配置（关键）

由于系统返回的是 HTML 页面，发帖成功后 `bid` 藏在首页列表的链接里（形如 `/blog/read/2c9f...`），需要用正则从**响应文本**中提取：

| 配置项 | 取值 |
|---|---|
| 提取来源 | Response Text（不能用 Response JSON，因为响应不是 JSON） |
| 提取方式 | 提取部分 → 正则表达式 |
| 正则表达式 | `/blog\/read\/([0-9a-zA-Z-]+)/` |
| 提取结果 | `$1` |
| 变量名 | `bid`（临时变量） |

## 三、场景二：安全-接口测试

前 3 步刻意在**未登录**状态下执行，用「不携带登录态」的方式模拟越权访问。

| 步骤 | 接口 | 方法与路径 | 关键参数 | 断言 | 预期（业务正确值） | 实际 | 结果 |
|---|---|---|---|---|---|---|---|
| 1 | 博客列表（分页） | GET `/blog/{page}/{limit}` | Path：`page=1`、`limit=10`，**不带 Cookie** | HTTP Code 等于 **200** | 302 跳登录 | 200 | 通过（脚本按实际值锁定，缺陷 BUG-03） |
| 2 | 打开发帖页 | GET `/blog/write` | 不带 Cookie | HTTP Code 等于 **500** | 302 跳登录 | 500 | 通过（缺陷 BUG-01） |
| 3 | 博客详情 | GET `/blog/read/{bid}` | Path：`bid=00000000000000000000000000000000`，不带 Cookie | HTTP Code 等于 **500** | 302 跳登录 | 500 | 通过（缺陷 BUG-02） |
| 4 | 登录 | POST `/login` | Body：`username=admin`、`password=123456` | HTTP Code 等于 **200** | 200 | 200 | 通过 |
| 5 | 博客列表（分页） | GET `/blog/{page}/{limit}` | Path：`page=0`、`limit=10` | HTTP Code 等于 **200** | 400 参数错误 | 200 | 通过（缺陷 BUG-05） |
| 6 | 博客详情 | GET `/blog/read/{bid}` | Path：`bid=0000...0000`（不存在） | HTTP Code 等于 **500** | 404 | 500 | 通过（缺陷 BUG-04） |
| 7 | 删除博客 | GET `/blog/delete/{uid}/{bid}` | Path：`uid=1`、`bid=0000...0000` | HTTP Code 等于 **200** | 404 或提示失败 | 200 | 通过（缺陷 BUG-04） |
| 8 | 博客列表（分页） | GET `/blog/{page}/{limit}` | Path：`page=1`、`limit=999999` | HTTP Code 等于 **200** | 400 或限制上限 | 200 | 通过（缺陷 BUG-05） |

> 说明：场景二的断言对象是「当前实际返回码」，作用是**把缺陷现状固化为回归基线**——开发修复后返回码会变，脚本立即报警。用例的真实预期见《02-接口测试用例表.md》，那里这 7 条判定为「不通过」。

> 为什么断言统一用 `HTTP Code`：本系统是 Thymeleaf 服务端渲染，接口返回 HTML 而非 JSON，`Response JSON` 断言无对象可用；`Response Text` 断言虽然可用，但页面文案会随模板调整而变化，稳定性差。因此状态码是这套系统里最稳定、最有回归价值的断言对象。
