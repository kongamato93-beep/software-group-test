# 狂神の小社区（kuang_simple_bbs）接口文档

> 本文档为《实验八 系统测试》Web API 接口测试部分的被测接口清单，与同目录 `kuang-bbs-openapi.json`（OpenAPI 3.0）内容一致。
> 文档由源码 `com.kuang.controller` 下 10 个 Controller 的路由注解逐一梳理得到，共 **37 条路径 / 40 个操作**，覆盖系统全部可访问端点。

## 一、被测系统与测试环境

| 项 | 内容 |
|---|---|
| 被测系统 | 狂神の小社区（kuang_simple_bbs / kuangstudy 0.0.1-SNAPSHOT） |
| 服务地址 | `http://localhost:8080` |
| 技术栈 | Spring Boot 2.3.0 + Spring Security + MyBatis-Plus 3.0.5 + Thymeleaf + MySQL |
| 认证方式 | Spring Security 表单登录，会话保持（Cookie：`JSESSIONID`） |
| 测试账号 | `admin` / `123456` |
| 接口测试工具 | Apifox 桌面版（项目名：狂神小社区-API接口测试） |
| 运行环境 | Windows 11、JDK 1.8、MySQL 8.x |

### 重要接口特征（影响断言设计）

1. **服务端渲染，不返回 JSON**。本系统是 Thymeleaf 模板渲染的 Web 应用，绝大多数接口响应体是 HTML 页面，`Content-Type: text/html;charset=UTF-8`。因此接口断言以 **HTTP 状态码 + 响应文本关键字** 为主，而不是 JSONPath 字段断言。
2. **写操作用表单提交**。POST 类接口的请求体为 `application/x-www-form-urlencoded`，不是 `application/json`。
3. **写操作成功后重定向**。发帖、评论、删除等在业务成功后执行 `redirect:/`，Apifox 会自动跟随重定向，最终状态码为 200。
4. **登录态靠 Cookie 传递**。自动化场景中，登录步骤之后的请求复用同一个 Apifox 环境会话，无需手动传 token。

## 三、核心接口详细说明

### 3.1 POST /login（登录）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/login` |
| 方法 | POST |
| Content-Type | `application/x-www-form-urlencoded` |
| 请求参数 | `username=admin`、`password=123456` |
| 成功响应 | 302 重定向到 `/`，Apifox 跟随重定向后得到 **200**，响应体为首页 HTML |
| 失败响应 | 302 重定向到 `/toLogin?error`，最终 **200**，响应体为登录页 HTML |
| 说明 | 由 Spring Security 的表单登录过滤器处理，不是自定义 Controller 方法；因此不能靠状态码区分成功与失败，需配合响应文本断言 |

### 3.2 GET /blog/{page}/{limit}（博客列表分页）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/blog/1/10` |
| 方法 | GET |
| Path 参数 | `page`（页码，从 1 开始）、`limit`（每页条数） |
| 成功响应 | 200，返回博客列表页 HTML，包含标题、作者、浏览量、分类等 |
| 说明 | 该接口**未做登录拦截**，匿名可直接访问（缺陷 BUG-03）；同时对 page=0、limit=999999 等非法值不做校验（缺陷 BUG-05） |

### 3.3 POST /blog/write（发表博客）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/blog/write` |
| 方法 | POST |
| Content-Type | `application/x-www-form-urlencoded` |
| 请求参数 | `title`（标题）、`content`（正文）、`authorId`、`authorName`、`authorAvatar`、`categoryId`（分类 id，取 1） |
| 成功响应 | 302 重定向到 `/`，最终 **200**；新帖出现在首页列表第一条 |
| 说明 | 业务成功后 `redirect:/`，因此判断发帖成功不能只看状态码，需再请求列表校验首条标题 |

### 3.4 GET /blog/read/{bid}（博客详情）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/blog/read/{bid}` |
| 方法 | GET |
| Path 参数 | `bid`（博客业务 id，32 位十六进制字符串，不是自增 id） |
| 成功响应 | 200，返回博客详情页 HTML |
| 异常响应 | 当 bid 不存在时，服务端未做空值判断，返回 **500**（缺陷 BUG-04） |
| 说明 | bid 需要从列表页或首页 HTML 中提取，是自动化场景中变量传递的关键 |

### 3.5 POST /blog/comment/{bid}（发表评论）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/blog/comment/{bid}` |
| 方法 | POST |
| Path 参数 | `bid` |
| 请求参数 | `topicId`（=bid）、`userId`、`userName`、`userAvatar`、`content`（评论内容） |
| 成功响应 | 302 重定向回详情页，最终 **200** |

### 3.6 GET /blog/delete/{uid}/{bid}（删除博客）

| 项 | 内容 |
|---|---|
| URL | `http://localhost:8080/blog/delete/{uid}/{bid}` |
| 方法 | GET（用 GET 做删除属于设计问题，见 BUG-05 说明） |
| Path 参数 | `uid`（作者 id）、`bid`（博客 id） |
| 成功响应 | 302 重定向到用户主页，最终 **200** |
| 异常响应 | uid/bid 不存在时仍返回 **200**，无任何错误提示（缺陷 BUG-04） |

## 四、响应约定

本系统没有统一的 JSON 响应包装类（源码中虽有 `R.java` 统一返回结果，但接口测试涉及的 Controller 全部返回视图名，未使用 `R`），实际响应形态如下：

| 场景 | 状态码 | Content-Type | 响应体 |
|---|---|---|---|
| 页面渲染成功 | 200 | text/html;charset=UTF-8 | 完整 HTML 页面 |
| 业务成功（写操作） | 200（跟随 302 后） | text/html;charset=UTF-8 | 目标页面 HTML |
| 资源不存在 / 未捕获异常 | 500 | text/html 或 application/json | Spring Boot 错误页 |
| 路径不存在 | 404 | text/html 或 application/json | Spring Boot 错误页 |

> 结论：对本系统做接口断言时，`HTTP Code` 是最稳定的断言对象；`Response JSON` 断言基本不可用，`Response Text` 断言适合校验页面是否渲染出关键内容。

## 五、导入 Apifox 的方式

1. 打开 Apifox → 新建项目 → 「导入数据」→ 选择 `Api` 格式 → 上传 `kuang-bbs-openapi.json`。
2. 导入后得到 5 个分组（认证与会话、博客模块、问答模块、用户与资料、公共页面），共 40 个接口。
3. 在「环境管理」中新建环境「本地开发环境」，前置 URL 填 `http://localhost:8080`。
4. 需要登录态的接口，先执行 `POST /login`，Apifox 会自动保存并复用 `JSESSIONID` Cookie。

> 注：`kuang-bbs-openapi.json` 是 OpenAPI 3.0 格式，用 Apifox 的「OpenAPI/Swagger」导入入口可直接识别。
